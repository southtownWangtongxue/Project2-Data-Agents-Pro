## 阶段一：日志显示实际调用模型 + 排查"还是报错"
- `backend/app/core/llm.py`：新增 `describe_route()`，返回 `provider_id / model / base_url / api_key前缀`。
- `backend/app/api/v1/chat.py`：`_stream_chat` 与 `_stream_chat_deepagent` 入口各加日志 `[LLM路由] 实际调用`；两处异常处理旁附带路由并将前端报错信息追加 `（实际模型: xxx）`。
- 诊断脚本确认：默认 provider `zhipu-glm4-flash` → 实际 model=`glm-4.5-air`，base=`https://open.bigmodel.cn/api/paas/v4`。
- 浏览器验证：报错信息变为 `处理异常: Connection error.（实际模型: glm-4.5-air）` → 改动生效。

## 阶段二：定位 task 模式 Connection error 的根因
- `.env` 中 `OPENAI_API_KEY=sk-8250...`（DashScope 的 key）且 `OPENAI_BASE_URL` 未设置（默认 `api.openai.com`）。
- `harness.py` 原 `_build_model_string()` 返回 `"openai:glm-4.5-air"` 字符串传给 `create_deep_agent` → `init_chat_model("openai:...")` → 读 `OPENAI_API_KEY`/`OPENAI_BASE_URL` → 拿到 DashScope key + 默认 OpenAI 端点 → Connection error。
- 用户独立测试 `init_chat_model(model='glm-4.5-air', api_key=ZHIPU_API_KEY, base_url=ZHIPU_BASE_URL)` 可以正常返回 → 证明模型/凭证没问题，是 DeepAgent 路径未显式传凭证。

## 阶段三：修复并验证
- `harness.py`：`_build_model_string()` → `_build_model()`，显式调用 `init_chat_model(model="glm-4.5-air", model_provider="openai", api_key=<ZHIPU>, base_url=<ZHIPU>, use_responses_api=False)` 返回 `BaseChatModel` 实例，直接传给 `create_deep_agent`。
- `get_deep_agent()` 是全局单例，改 `harness.py` 后需整进程重启（uvicorn reload 不清单例）。
- 用户重启后端，浏览器 E2E 验证：通用任务发送"用三句话简单介绍一下机器学习的基本概念" → 返回真实回答，无 Connection error，状态 ✓ 完成。
