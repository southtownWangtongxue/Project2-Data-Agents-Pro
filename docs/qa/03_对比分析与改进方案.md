## 〇、摘要：一句话结论

> **DataAgent Pro 是一个"功能齐全的业务型 Agent 应用"，DeepSeek Harness 是一个"可重组的 Agent 运行时"。**
> 两者不在同一层：本项目的差距不在"能不能做"，而在**能不能被替换、被观察、被信任**。
> 最急需补齐的三件事：**高危判定的 deny-by-default**、**MCP 接入运行时**、**"所见即所记"的事件溯源**。

### 综合评分卡

| 维度 | DataAgent Pro | DeepSeek Harness | 差距 | 关键结论 |
|------|:-------------:|:----------------:|:----:|---------|
| 核心功能 | 7.5 / 10 | 8.5 / 10 | 中 | 业务链路（Text-to-SQL）更垂直；通用执行能力（shell/fs/code）缺失 |
| 系统提示词 | 6.5 / 10 | 9.0 / 10 | 大 | 已有分层组装雏形，但缺变量插值、作用域、运行时上下文与瀑布改写点 |
| 工作流程 | 7.0 / 10 | 9.0 / 10 | 大 | LangGraph 图编排够用；缺 turn/step 语义、请求可重建性与中断恢复契约 |
| 工具调用 | 5.5 / 10 | 9.0 / 10 | **极大** | 无 pre/post 瀑布、无守卫、无超时重试、无结果归一化 |
| 对话界面 | 7.5 / 10 | 8.5 / 10 | 中 | 组件与流式体验完整；缺按来源可检查的 Trajectory 视图 |
| 高危权限 | 4.0 / 10 | 9.5 / 10 | **极大** | 正则前缀匹配可被绕过；**拒绝未作为默认路径** |
| 界面动效 | 7.0 / 10 | 7.5 / 10 | 小 | 动效丰富度接近；缺无障碍降级 |
| 高级配置（MCP/Skill） | 4.5 / 10 | 9.0 / 10 | **极大** | MCP 仅配置未接入运行时；Skill 无渐进式披露 |

## 一、对比基准：DeepSeek Harness 是什么

| 项 | 内容 |
|----|------|
| 定位 | Agent **运行时中间件**（Harness 层），不绑定模型、不抢用户界面 |
| 技术栈 | TypeScript / Node.js，底层插件内核 [Cordis](https://github.com/cordiverse/cordis)；提供 Python SDK（JSON-RPC 桥接） |
| 状态 | Developer Preview，官方明示"会有破坏性变更" |
| 启动 | `npx @deepseek-ai/dsh web`（默认 `127.0.0.1:3080`） |
| 核心信条 | **Everything is a Plugin** + **Every run is traceable** |

### 1.1 分层结构

```
入口层   apps/ (CLI / Web) + packages/boot  ← Profile + Bundle + Patch 三层叠配置
调度层   core/agent · core/agent-loop · core/session · core/system-prompt
执行层   core/tools + shell/ · terminal/ · fs/ · subprocess/ · jobs/
扩展层   llm/（模型适配器）· mcp/ · subagent/ · skill/ · plan/ · todo/ · compaction/ · lsp/
安全层   sandbox/ · guard/ · credentials/ · native/（Linux Landlock 启动器）
```

### 1.2 核心包与 ctx 键

| 包 | 职责 | ctx 键 |
|----|------|-------|
| `core/session` | 只追加 `SessionEvent` 日志与内存存储 | `ctx.sessions` |
| `core/system-prompt` | 提示词分段与工具 schema 组装 | `ctx.systemPrompt` |
| `core/tools` | 作用域化工具注册表 + 带守卫的执行流水线 | `ctx.tools` |
| `core/agent` | Agent 接口、实时注册表、`agent/*` 事件 | `ctx.agents` |
| `core/agent-loop` | 默认循环驱动器 | `ctx.agentLoop` |
| `llm/llm` | 消息/流式词汇 + 适配器缝合点 | `ctx.llm` |

### 1.3 四种运行模式

| 模式 | 定位 |
|------|------|
| **Standard** | 完整编码 Agent：文件编辑、shell、搜索、skills、planning、goals、subagents、workflows |
| **Code** | 工具经 Code Mode SDK 暴露，模型用一段 TypeScript 编排多步调用 |
| **Minimal** | 仅持久化 bash + str_replace_editor，用于模型能力基准测评 |
| **Creator** | 运行时自检、内存中试跑 Cordis 插件、组合出新模式 |

## 二、八维度详细对比

### 维度 1：核心功能

| 能力 | DataAgent Pro | DeepSeek Harness |
|------|--------------|------------------|
| 主场景 | **Text-to-SQL 业务数据问答**（垂直） | 通用编码/运维 Agent 运行时（横向） |
| Agent 编排 | LangGraph 1.x 状态图 + 8 个专家 Agent（orchestrator/rag/schema/sql_coder/security/analyst/reporter/misc）+ quality_evaluator、title_generator | Cordis 插件树 + `core/agent-loop` 循环驱动器，Agent 本身是插件 |
| 双引擎 | legacy 工作流 与 DeepAgent（`mode=task` 时强制）并行存在 | 单一循环驱动器，模式差异由插件组合（Profile）表达 |
| 会话能力 | 列表/重命名/恢复/fork/长期目标/轨迹/导出（**实测均可用**） | fork / resume / replay / search / list / page / follow，全部基于同一事件流 |
| 通用执行 | ❌ 无 shell / 文件编辑 / 进程 / LSP | ✅ shell、terminal、fs、subprocess、jobs、lsp 全套 |
| 上下文管理 | 无压缩 | `compaction/` 上下文压缩插件 |

**差距分析**

1. **能力边界过窄**。本项目所有能力都收敛在"查数据 → 分析 → 出图"，一旦用户提出"把这个结果写成文件""跑个脚本"，链路即失效。Harness 的 shell/fs/subprocess/jobs 是**插件**，可按需挂载——本项目不一定要全做，但**执行层应具备可插拔的扩展位**（见改进方案 R1）。
2. **双引擎并存带来认知与维护成本**。`USE_DEEP_AGENT` + `mode=task` 强制切换，两条代码路径（ `_stream_chat` / `_stream_chat_deepagent`）行为不完全一致（实测 legacy 可跑通、DeepAgent 因模型异常直接 error 中断）。Harness 用 Profile+Bundle 表达模式差异，**只有一套循环**。
3. **会话 fork 语义不同**。本项目 fork 实测 `copied_events: 0`（事件溯源关闭导致空拷贝）；Harness 的 fork 要求"所选前缀必须结束于开放 turn 之外"，否则**拒绝而非静默裁剪**——这是值得直接借鉴的强约束。

### 维度 2：系统提示词设计

#### 本项目现状

`app/deepagent/prompts.py` + `app/core/prompt_section.py`：

```python
assembler.add("harness_identity", -100, "你是 Data Agent Pro 的智能调度中心…")
assembler.add("core_duties",        0, "## 核心职责 …")
assembler.add("subagent_rules",   100, "## 子 Agent 委派规则 …")
assembler.add("complex_task",     150, "## 复杂任务处理流程 …")
assembler.add("task_examples",    160, "## 任务规划示例 …")
assembler.add("skills",           200, "## 可用专业技能 (Skills) …")   # 条件注入
assembler.add("guidelines",       300, "## 重要准则 …")
```

同时保留 `_build_system_prompt_legacy()` 单字符串旧版，由 `PROMPT_SECTION_ENABLED` 切换。

#### Harness 设计

`ctx.systemPrompt` 注册契约：

```ts
interface PromptSection {
  readonly name: string                       // 唯一名，重复注册抛错
  readonly order: number                      // 升序拼接，同序按 name 代码单元序
  readonly text: string | ((ctx: AssembleContext) => string)   // 支持 {{变量}}
  readonly complete?: boolean                 // 独占模式：成为唯一提示词段
}
```

关键机制：

| 机制 | 说明 |
|------|------|
| **集中分配 order** | `getSectionOrder(name)` / `getContextOrder(name)`，避免各插件硬编码顺序打架 |
| **变量插值** | `ctx.systemPrompt.variable(name, provider)`，段内 `{{name}}` 在渲染期插值 |
| **动态上下文 `PromptContext`** | 与 `PromptSection` 分离，缓存安全；**仅当内容变化或压缩移除历史后才重新快照** |
| **作用域遮蔽** | 作用域内注册的段/变量**遮蔽**同名全局项，实现 per-agent preset 差异 |
| **工具 schema 提供者** | `tools(provider)` 返回 `ToolProviderResult{schemas, knownNames}`，每次组装实时求值 |
| **组装瀑布 `system-prompt/assemble`** | 作用域过滤的 waterfall，返回值权威，插件可改写整体结果 |
| **变更通知** | `system-prompt/change` 事件驱动热刷新 |

#### 差距

| # | 差距 | 影响 |
|---|------|------|
| G2-1 | 无变量插值与运行时上下文分离 | 环境信息（数据源清单、当前时间、用户权限）只能硬编码或全量重算，无法缓存 |
| G2-2 | 无作用域（scope）概念 | 无法为 data/report/doc/task 各模式提供差异化提示词，只能整体字符串拼接 |
| G2-3 | 无组装期瀑布扩展点 | 第三方/插件无法在组装最后一步改写提示词 |
| G2-4 | 无 `complete`（独占）能力 | 无法做"极简模式"这类整体替换提示词的场景 |
| G2-5 | 无集中 order 分配 | 多人协作时 order 硬编码易冲突 |
| G2-6 | **无 prompt injection 防御段**（实测确认） | 用户输入可影响系统指令边界 |

> 客观评价：本项目的 **PromptSection 分层 + 条件注入 Skill 段 + 新旧版 A/B** 已是正确方向，与 Harness 的理念一致，差距主要在**工程完备度**（变量、作用域、瀑布、热刷新）而非方向。

### 维度 3：工作流程

#### 本项目

```
用户输入 → clarify_plan（意图分析+计划）
  → schema_agent → sql_coder → security ─┬─ safe → execute_sql → quality_gate
                                         │          → analyst → reporter → finish
                                         └─ dangerous → interrupt → 人工审批 → resume / reject
  → rag_agent（知识咨询分支）
```
- LangGraph 条件边路由；`interrupt()` / `Command(resume=...)`；Redis checkpointer，TTL 1 小时。
- 实测事件序列：`thread_id → node_started → thinking → plan → tool_call → tool_result → title → done`。

#### Harness

```
turn/start
  claim next-step input + queued messages
  assemble prompt sections + tool schemas
  → agent/pre-step            ← 可改写 claimed messages，或直接 reject
    step/start
    append entered messages as user/message
    derive model history from log
    agent/request → llm/stream → assistant/chunk* → assistant/message
    tool/call* → tools/pre-execute → tools/execute → tools/post-execute → tool/result*
    step/end
    工具仍需请求 或 有新输入 → 认领 → 下一步
  → agent/turn-stopping
turn/end
```

| 概念 | 语义 |
|------|------|
| **step** | 一次模型请求 + 它调用的工具 |
| **turn** | 零或多个 step；开启于认领首个输入，关闭于"不再欠工作" |
| `agent/pre-step` | 瀑布，**决定模型看到什么**；可改写或拒绝；被拒绝/空 claim 仍会记录一个未消耗 step 的持久 turn |
| `agent/turn-stopping` | 串行事件（无 `next()`），用于停止整个 turn |
| `request/header` | 完整请求信封快照，使**每次对话请求成为日志的纯函数** |

#### 差距

| # | 差距 | 影响 |
|---|------|------|
| G3-1 | **缺 turn/step 语义** | 无法表达"这一步模型请求了什么、调用哪些工具、消耗多少 token"；重试、计费、审计粒度只能到"节点" |
| G3-2 | **缺 `agent/pre-step` 关卡** | 没有任何插件能在请求发出前改写或拒绝；上下文注入只能硬编码在各节点内 |
| G3-3 | **模型历史不从日志派生** | 本项目历史存 MySQL `chat_nodes`、上下文存 Redis checkpoint，二者可能不一致；Harness 是"派生而非副本"，并有运行时断言 |
| G3-4 | 中断恢复依赖 Redis TTL 1h | 审批等待超 1 小时任务即失效且无提示；Harness 的 `session/end-seed` 能从持久化字节定位实时起点 |
| G3-5 | 取消（cancel）为标志位 break | Harness 有明确的 `TurnEndCancelCause` 与崩溃恢复合成的 `interrupted` 原因 |

### 维度 4：工具调用

#### 本项目

- DeepAgent 固定工具：`get_fixed_tools()` → 百度联网搜索（经 `seam` 能力缝合点解析）。
- Skill 执行器：`create_skill_tools()` 把已启用 Skill 的执行器注册为工具。
- SSE 下发：`tool_call{name,args}` / `tool_result{name,status,content}`。
- 子 Agent：data-query、knowledge-retrieval 两个 `CompiledSubAgent`。

#### Harness 工具执行流水线

```
Assistant 消息含 tool-call 块
  → tool/call（会话事件，执行前即记录）→ UI pending card
  → tools/pre-execute 瀑布        ← hooks、permission、sandbox
  → 注册的单调守卫（monotonic guards）   ← deny / abstain
  → ctx.approval 一次性提示          ← 缺席或无法回答 = deny
  → tools/execute 瀑布（around dispatch）← timeout、retry、metrics
  → 工具 execute() 本体
  → fs/write-intent / fs/edit-intent 门（仅 tool-fs 变更）
  → 工具自有会话事件（todo/write、fs/observed、hook/invoked…）
  → tools/post-execute 瀑布        ← accept / block / replace / add context
  → 注册表外层归一化（快照异常 → isError）
  → ToolDefinition.finalizeContent  ← 内容不变式最后一道
  → tools/result 同步通知（冻结的权威结果）
  → 活跃批次 additionalContexts FIFO 注入
  → tool/result（会话事件，单一模型可见结果）→ UI completed card
```

#### 差距

| # | 差距 | 影响 |
|---|------|------|
| G4-1 | **无 pre/post 执行瀑布** | 无法在不改工具本体的前提下挂超时、重试、审计、结果改写 |
| G4-2 | **无守卫（guard）机制** | 权限策略与工具实现耦合，无法跨工具族统一 |
| G4-3 | **无超时/重试/指标** | 实测单查询 42s，无节点级耗时埋点可定位 |
| G4-4 | **无结果归一化与内容不变式** | 工具抛异常与业务错误边界模糊 |
| G4-5 | MCP 未接入（详见维度 8） | 工具生态无法外扩 |
| G4-6 | 子 Agent 仅 2 个且硬编码 | Harness 的 subagent 是**可替换的缝合点**，甚至有实验性 Agent Teams |

> 值得肯定：本项目的 `app/core/seam.py` **能力缝合点**设计与 Harness 的 seam 三角色（声明方 / 提供方 / 消费方）理念高度一致，已用于搜索后端可替换。这是很好的基础设施，应扩展到更多能力。

### 维度 6：高危动作权限管理（**差距最大**）

#### 本项目实现

```python
_SAFE_PATTERN      = r"^\s*(?!--\s|/\*)(SELECT|SHOW|DESCRIBE|DESC(?!\b\w)|EXPLAIN)\b"
_DANGEROUS_PATTERN = r"^\s*(?!--\s|/\*)(INSERT|UPDATE|DELETE|DROP|TRUNCATE|ALTER|CREATE|REPLACE)\b"

if safe_match and not dangerous_match:  → safe
if dangerous_match:  → LLM 二次确认 → 无论如何都返回 dangerous（保守）
未匹配任何关键词:      → 返回 safe      ← ⚠️ 兜底为"放行"
```

审批：`POST /api/v1/approve {task_id, action: approve|reject, comment}`，`Command(resume=...)` 恢复图执行。

#### 实测结果（9 条分类用例，5 通过 / 4 失败）

| 用例 | 输入 | 期望 | 实测 | 结论 |
|------|------|------|------|------|
| TC-SEC-04 | `SELECT id FROM t` | safe | safe | ✅ |
| TC-SEC-05 | `DELETE FROM users WHERE id=1` | dangerous | dangerous | ✅ |
| TC-SEC-06 | `DROP TABLE users` | dangerous | dangerous | ✅ |
| TC-SEC-11 | `UPDATE users SET role='admin'` | dangerous | dangerous | ✅ |
| **TC-SEC-07** | `SELECT * FROM t; DROP TABLE users` | dangerous | **safe** | ❌ **绕过** |
| **TC-SEC-08** | `GRANT ALL ON *.* TO 'hacker'@'%'` | dangerous | **safe** | ❌ **绕过** |
| **TC-SEC-09** | `EXEC xp_cmdshell('rm -rf /')` | dangerous | **safe** | ❌ **绕过** |
| **TC-SEC-10** | `SELECT * INTO newtable FROM old` | dangerous | **safe** | ❌ **绕过** |

其他实测缺陷：
- **审批缺乏职责分离**：任意登录用户可审批自己发起的高危 SQL（TC-SEC-01 暴露）。
- **审批状态无处可查**：`/approval` 页显示"0 待审批"，因为 Redis checkpoint 与页面数据源未打通。

#### Harness 设计

| 机制 | 说明 |
|------|------|
| **单调守卫（monotonic guards）** | 注册式守卫，只能 deny 或 abstain；已确认的放行不可被后续守卫推翻 |
| **审批一次性提示** | `ctx.approval` 一次性 prompt；**缺席或无法回答 = deny** |
| **拒绝是默认路径** | 分类器超时、报错、答案模糊，**统统按"转人工"处理，而非放行** |
| **风险规则库** | 递归删除、系统路径写入、关机重启、服务停止、权限变更、包安装卸载、提权、读取密钥等 9 大类；命中后分类器**无否决权**，直接转人工 |
| **只读白名单** | 显式配置只读前缀，命中直接放行 |
| **alwaysAsk 开关** | 开启后该会话所有命令转人工 |
| **审批预设** | Read-only / Workspace Write / Full Access（Full Access 会跳过所有审批阶段，官方文档明示此风险） |
| **审计留痕** | 每次执行或拒绝记录一条会话事件：目标、脱敏后的命令、哪一关卡决定、原因与结果 |
| **纵深防御** | `sandbox/` + `guard/` + `credentials/` + `native/`（Linux Landlock 启动器）+ 流水线内审批把关 |

#### 差距

| # | 差距 | 严重度 |
|---|------|-------|
| G6-1 | **兜底策略错误**：未命中已知关键词 → 放行。应为 deny-by-default | **致命** |
| G6-2 | 正则只匹配语句首关键词，不做多语句拆分 | **致命** |
| G6-3 | 危险关键词为**枚举式黑名单**，必然存在覆盖盲区（GRANT/EXEC/SET/CALL/LOAD_FILE/OUTFILE…） | **致命** |
| G6-4 | LLM 二次确认**结果被丢弃**（无论 LLM 说什么都返回 dangerous），等于白跑一次调用、增加 3~5s 延迟 | 高 |
| G6-5 | 无单调守卫 / 无审批关卡链，只有单点的 security 节点 | 高 |
| G6-6 | 无审批预设（权限档位），无法按场景配置 | 中 |
| G6-7 | 审批无职责分离、无审计落库 | 高 |
| G6-8 | 无沙箱（仅有 SQL 层管控，无进程/文件隔离） | 中 |
| G6-9 | 审批等待受 Redis TTL 1h 限制，超时静默失效 | 中 |

> **核心理念差异**：Harness 把"拒绝"作为代码的**默认路径**（`absent or unanswerable → deny`）；本项目把"放行"作为默认路径（`未匹配到已知危险关键词，默认放行`）。这一行代码的方向差异，决定了整个安全模型的可信度。

**R1 参考实现（建议形态）**：

```python
_SAFE_STMT = re.compile(r"^\s*(SELECT|WITH|SHOW|DESCRIBE|DESC|EXPLAIN)\b", re.I)
_WRITE_HINT = re.compile(r"\b(INTO|OUTFILE|DUMPFILE|LOAD_FILE|FOR\s+UPDATE)\b", re.I)

def split_statements(sql: str) -> list[str]:
    """忽略字符串字面量与注释内的分号做切分。"""

async def classify_sql(sql: str) -> dict:
    for stmt in split_statements(sql):
        if not _SAFE_STMT.match(stmt):        # 非白名单 → 一律危险
            return {"category": "dangerous", "method": "whitelist",
                    "reason": f"语句不在只读白名单: {stmt[:40]}"}
        if _WRITE_HINT.search(stmt):          # SELECT INTO / OUTFILE 等写提示
            return {"category": "dangerous", "method": "write-hint",
                    "reason": "只读语句中含写操作特征"}
    return {"category": "safe", "method": "whitelist", "reason": "全部语句命中只读白名单"}
```

## 五、建议的落地顺序

```
第 1 周   R1 R2 R3 R4 R5 R6                 ← 止血：安全兜底反转 + 鉴权补漏 + 路由修复
第 2-3 周 R7 R8 R12 R13 R22                 ← 补能力：MCP 接线 + Skill 渐进披露 + 提示词工程
第 4-6 周 R9 R10 R11 R14 R15                ← 治理：工具流水线 + 审批关卡链 + UI 收敛
第 7 周+  R16 R17 R18 R19 R20 R21 R23       ← 架构：事件溯源统一 + Trajectory + seam 扩展
```

**优先级判断依据**：
1. **安全兜底方向错误（R1）优先于一切功能**——它使"改数据必批"这一核心承诺在 4 类 SQL 上失效。
2. **MCP 接线（R7）优先于新功能**——已完成的配置界面是沉没成本，接线即可产生价值。
3. **架构演进（R16+）放在最后**——它需要前两阶段打下的事件与流水线基础。

## 六、值得保留的本项目优势

对比不是为了否定。本项目有以下 Harness 不具备或不强调的优势，应在改进中保留：

| 优势 | 说明 |
|------|------|
| **垂直业务深度** | Text-to-SQL 全链路（Schema 过滤 → 方言适配 → 自纠错 → 质量门 → 分析 → 图表）是 Harness 完全没有的能力，这是本项目的护城河 |
| **多方言支持** | MySQL / PostgreSQL / Oracle / SQL Server 四种方言模板，`app/db/dialects/` 扩展不改核心逻辑 |
| **数据脱敏内置** | 手机号 / 身份证 / 邮箱脱敏开箱即用（实测符合预期），Harness 需自行实现 |
| **Seam 缝合点已有雏形** | `app/core/seam.py` 的三角色设计与 Harness 理念一致，是很好的扩展基座 |
| **提示词 A/B 能力** | 新旧版提示词语义等价可切换，便于审计与灰度，Harness 未强调此能力 |
| **SSE 协议覆盖面** | 21 种事件类型，含 `node_started`（节点开始即通知）、`reasoning`（思考隔离）等体验细节 |
| **首字节性能** | 实测 SSE 首字节 **17ms**，远优于 1s 目标 |
