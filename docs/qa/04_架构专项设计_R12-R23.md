## 一、为什么需要整体设计：耦合关系

剩余 6 项不是 6 个独立任务，而是同一个目标（"可重组的 Agent 运行时"）的 6 个切面：

```
R20 单一循环驱动器 ◄── R12 每请求级变量（需要每请求 prompt 组装）
       ▲                    ▲
       │                    │
R19 配置分层（Profile/Bundle/Patch，驱动器的模式表达机制）
       │
R16 turn/step 语义（统一循环的事件底座，双引擎归一的观测前提）
       
R14 统一 UI ◄── 独立于后端，但受 SSE 协议稳定性保护
R18 seam 扩展 + R23 执行层扩展 ◄── 依赖 R9 流水线 + R11 档位（已就绪）
```

若先做 R14/R23 而不动 R20，会继续在双引擎上叠加代码，将来归一时返工更大。因此推荐顺序：**事件底座（R16）→ 循环归一（R20）→ 配置分层（R19）→ 变量完全体（R12）→ UI 收敛（R14）→ 执行层（R18+R23）**。

## 三、目标形态

```
┌─────────────────────────────────────────────────────────────┐
│ 入口层  chat_completions（认证/压缩/路由 → 唯一入口）          │
├─────────────────────────────────────────────────────────────┤
│ 统一循环驱动器  AgentLoopRunner（R20）                        │
│   · 每请求组装：prompt（R12 变量）+ 历史压缩 + 工具集 + 档位   │
│   · 产出统一内部事件流（TurnEvent，R16）                      │
│   · SSE Adapter：TurnEvent → 21 种 SSE 事件（协议不变）       │
├─────────────────────────────────────────────────────────────┤
│ 引擎 Profile（可插拔，二选一执行）                             │
│   · legacy-graph：现 LangGraph 业务管线（原样封装，不改图）     │
│   · deepagent：deepagents 调度中心（task 模式）               │
├─────────────────────────────────────────────────────────────┤
│ 能力层（已就绪，驱动器统一调用）                                │
│   R9 工具流水线 · R11 审批档位 · R10 审计 · R8 Skill 披露      │
│   R7 MCP 运行时 · R21 上下文压缩 · seam 缝合点（R18 扩展位）    │
├─────────────────────────────────────────────────────────────┤
│ 状态/观测层                                                   │
│   R16 TurnEvent 事件溯源（session_events 扩展）+ Trajectory    │
│   R19 Profile/Bundle/Patch 配置分层 + dump-config             │
└─────────────────────────────────────────────────────────────┘
```

核心思想：**不是重写两条引擎为一条，而是让两条引擎成为同一驱动器的两个可插拔 Profile**。业务管线（legacy 图）原样保留——它是护城河；归一的是循环外围（prompt 组装、压缩、事件、SSE、审批、观测），消除双路径的行为漂移。

## 四、分项设计

### 4.1 R16 turn/step 语义与事件溯源统一（先行，其他项的地基）

**目标**：事件日志成为唯一事实源，"模型可见即已记录"。

- `session_events` 表扩展（兼容性迁移，同 run_id 列先例）：
  - 新列 `turn_id VARCHAR(64)`（= 现 session_thread_id 的会话轮次标识）、`step_order INT`（turn 内步骤序号）、`turn_event ENUM('turn_start','step_start','user_message','assistant_message','tool_call','tool_result','step_end','turn_end','tool')`——现有 event_type 值保留映射，不破坏 trajectory/export 现有消费端
  - `derive_messages(turn_id) -> list[dict]`：从事件日志派生 LLM 消息历史（user_message/assistant_message/摘要事件），供恢复会话与压缩摘要使用——**替代**前端逐条传全量 messages 的路径（渐进：先并行写入，验证一致后切换）
- **不变量断言**：任何进入 LLM 上下文的内容必须有对应已落库事件；开发模式下断言，生产记日志

**回滚**：新列与断言用 `TURN_EVENT_ENABLED` 开关；关闭即回到现状。

### 4.2 R20 单一循环驱动器（核心工程）

**目标**：`_stream_chat` / `_stream_chat_deepagent` 收敛为一个驱动器 + 两个 Profile。

- 新模块 `app/core/agent_loop.py`：
  ```python
  class AgentLoopRunner:
      def __init__(self, profile: LoopProfile): ...
      async def run(self, request: LoopRequest) -> AsyncIterator[TurnEvent]
  ```
  - `LoopRequest`：question / user / history(已压缩) / thread_id / mode / model / web_search / prompt(每请求组装，R12) / tools / policy(R11)
  - `LoopProfile` 协议：`build_input(request) -> Any`、`stream(request) -> AsyncIterator[原始事件]`、`extract(raw) -> TurnEvent`
  - 两个实现：`LegacyGraphProfile`（包装现 `_stream_chat` 内部逻辑的图调用段）、`DeepAgentProfile`（包装现 deepagent 分支）
- **SSE Adapter**：TurnEvent → 现 21 种 SSE 事件映射表（前端零改动）
- `chat_completions` 变为：认证 → 压缩 → 选 Profile → Runner.run → SSE
- **收益兑现点**：每请求 prompt 组装（R12 完全体）、双引擎行为对齐（DeepAgent 获得与 legacy 相同的审批/质量/压缩语义）、未来新增引擎 = 新增一个 Profile

**迁移步骤（渐进，不切换）**：
1. 建 `agent_loop.py` 骨架 + TurnEvent 适配器，legacy Profile 包装现有代码路径，**影子运行**（新旧并行执行，比对事件序列一致性，日志输出差异不对外）——跑 1~2 天真实流量
2. 影子比对通过后，`AGENT_LOOP_ENABLED` 开关切换默认路径
3. 观察一周后删除旧分发代码

**回滚**：`AGENT_LOOP_ENABLED=false` 一键回旧路径（旧代码在影子期完整保留）。

### 4.3 R12 运行时变量（完全体）

- 驱动器每请求调用 `build_system_prompt(skills, variables={"app_name","app_version","user_name","today","mode","tier"})`
- DeepAgent 单例约束的解法：`create_deep_agent` 的 system_prompt 参数改为接收**每请求可变的注入方式**——两种方案：
  - **方案 A（推荐）**：中间件注入——deepagents 支持 middleware，在 `before_agent` 阶段把每请求变量写入系统消息（现 PatchToolCallsMiddleware 同位），prompt 模板保持 `{{var}}` 占位
  - 方案 B：每请求重建 agent（成本高，放弃）
- 作用域段：PromptAssembler 的 scope 机制按 mode 启用（data/task 各自专属段落）

### 4.4 R19 Profile / Bundle / Patch 配置分层

- 目标：8 个散落开关收敛为**分层配置**：
  - `configs/profiles/base.json`（默认层：所有开关的出厂值）
  - `configs/profiles/{mode}.json`（模式层：data/task 覆盖，如 task 强制 deepagent profile）
  - `configs/patch.json`（用户补丁层：运维临时覆盖，优先级最高）
- ConfigManager 扩展 `get_effective(key)` 按层合并；`GET /config/effective` dump 全量生效配置（审计用）
- 兼容：旧开关名在合并层中保留别名，旧代码路径开关语义不变

### 4.5 R14 统一 UI（决策点最多的项）

- **推荐方案**：以 **Chat.vue（Element Plus 系）为主体收敛**，吸收 ChatX 的视觉优点（AntDX 的 Welcome/Prompts 交互样式可用纯 CSS 复刻）——理由：Chat.vue 承载全部功能（轨迹面板 R17、统计条、审批、导出、并行图卡片），ChatX 仅为壳；反之迁移功能到 AntX 工作量数倍
- 步骤：① ChatX 从路由降级为实验入口 → ② 对比期收集使用数据 → ③ 删除 ChatX 路由与 x/ 组件（保留 git 历史）
- **待用户拍板**：是否接受删除 AntDX 依赖（package.json 减重）；或反向收敛到 AntX（不推荐）

### 4.6 R18 seam 扩展 + R23 执行层扩展（合并实施）

- seam 扩展服务清单：`llm`（现 set_provider 迁入）、`vectorstore`（Milvus）、`export`（csv/excel）、`fs`、`shell`
- R23 执行层：新增受控工具 `run_sql_script`（已有）之外的 `write_file`（导出目录白名单）/ `run_command`（命令白名单 + 超时 + 无网络），**全部经 R9 流水线 + R11 档位管控**：
  - read_only 档：shell/fs 工具直接拒绝
  - workspace_write 档：write_file 允许（限导出目录），run_command 需审批
  - full_access 档：自动放行但全量审计
- 安全边界：工作目录白名单（仅 `exports/`）、命令黑名单（rm/sudo/curl 等）、输出大小限制
